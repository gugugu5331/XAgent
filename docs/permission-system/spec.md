# Permission System Spec

## 背景

XAgent 已具备工具系统、Agent Loop、路径沙箱基础和危险工具确认流程，但当前权限控制仍比较粗：工具只按 `RiskSafe` / `RiskDangerous` 判断是否需要确认，Plan Mode 只读限制也只覆盖当前模式。随着 Agent Loop 能自主连续调用工具，系统需要更强的权限层来限制危险操作、控制文件范围、让用户按信任等级切换策略，并在权限被拒绝时让模型继续调整方案。

本章目标是为 XAgent 增加五层防御的权限系统：危险操作硬拦截、路径沙箱、可配置规则、权限模式、人机确认。权限系统必须在工具执行前统一决策，并把拒绝结果作为可恢复 tool result 回灌给模型，而不是终止 Agent Loop。

## 目标

- 在执行工具前硬拦截不可放开的高危命令和不可越过的模式约束。
- 继续保证文件读写只能发生在项目目录内，并以解析符号链接后的真实路径做判断。
- 支持独立的用户级、项目级、本地级 YAML 权限规则文件。
- 支持按工具名和参数/路径模式声明 `allow` 或 `deny`。
- 支持多档权限模式，让用户整体切换严格、默认、放行等信任等级。
- 支持人在回路确认，规则未明确命中时可让用户选择拒绝、本次允许、本会话允许、永久允许。
- 支持确定性的规则优先级：硬约束最高，会话级临时规则高于文件规则，本地级高于项目级，项目级高于用户级。
- 权限拒绝不会终止 Agent Loop，而是作为可恢复工具结果返回，让模型有机会改用安全策略。

## 功能需求

- F1: 系统必须在工具执行前经过统一权限决策流程，决策结果至少包括 allow、deny、ask。
- F2: 权限决策必须集中在独立组件中完成；Orchestrator 负责处理 ask 的 UI 往返，Executor 执行前必须能再次依赖最终授权，避免绕过 Orchestrator 直接执行工具。
- F3: 硬约束必须在任何可配置规则、权限模式和用户确认之前执行；命中硬约束时必须 deny，且不能被配置或用户确认放开。
- F4: 硬约束至少包括：危险 Bash 黑名单、路径沙箱失败、Plan Mode 只读限制、权限系统自身配置文件保护、明显提权或系统破坏操作。
- F5: Bash 黑名单必须支持正则匹配命令，至少覆盖强制删除、磁盘格式化、权限破坏、系统关机重启、fork bomb、提权、写系统目录、破坏 git 历史等高危模式。
- F6: Bash 黑名单不能作为唯一安全边界；普通 Bash 授权应优先通过 allowlist 风格规则表达安全命令族，未明确允许的复杂 shell 命令应进入 ask 或 deny。
- F7: 路径沙箱必须继续限制文件相关工具只能访问项目目录内路径；判断前必须解析符号链接和最深已存在祖先，防止路径逃逸。
- F8: 路径沙箱失败必须 deny，且不能被规则、权限模式或用户确认覆盖。
- F9: 文件工具规则匹配必须基于规范化后的项目相对真实路径，同时保留展示用原始路径；不得通过 `../`、重复分隔符、symlink 别名或 Unicode 变体绕过规则。
- F10: 权限规则必须支持「工具名(模式)」展示格式，例如 `Bash(git status)`、`Bash(git *)`、`Read(docs/**/*.md)`、`Edit(internal/**/*.go)`。
- F11: 持久化 YAML 必须使用明确 schema，而不是只保存一段字符串；每条规则至少包含 tool、pattern、match_type、effect，可选包含 path_param、description。
- F12: 每条规则结果只能是 `allow` 或 `deny`。
- F13: 规则匹配必须支持 exact 和 glob；硬黑名单支持 regex。普通 allow/deny 规则是否支持 regex 留给 plan.md 决策，但默认不应让 regex 成为项目规则的必需能力。
- F14: Bash 规则的模式匹配命令字符串，但必须定义空白规范化、完整字符串锚定和 shell 组合命令处理；`Bash(git *)` 不应放行 `git status && rm -rf .` 这类组合命令。
- F15: 文件工具规则的模式匹配规范化后的项目相对路径；glob 语义必须明确 `*` 和 `**` 的目录匹配范围。
- F16: 权限规则必须支持三层独立 YAML 文件：用户级、项目级、本地级；越靠近项目优先级越高。
- F17: 用户级应位于用户配置目录；项目级可提交仓库；本地级必须用于本机私有授权，默认不应提交到 git；永久允许只能写入本地级规则文件。
- F18: 会话级临时规则必须覆盖所有文件规则，用于实现“本会话允许”。会话级规则仅存在于运行期内存，不写入 conversation history。
- F19: 最终优先级必须确定：硬约束（含 Plan Mode、黑名单、路径沙箱） > 会话级规则 > 本地级规则 > 项目级规则 > 用户级规则 > 权限模式默认策略 > ask。
- F20: 同一层级多条规则同时命中时，必须采用确定性语义；默认 deny 优先于 allow，或在 plan.md 明确更具体规则优先/文件顺序策略。
- F21: 权限模式必须至少包含 strict、default、permissive 三档。
- F22: 权限模式只处理未命中显式规则的默认策略，不得覆盖显式 deny、硬约束或 Plan Mode 只读限制。
- F23: strict 模式下，未明确 allow 的危险操作必须 ask 或 deny；default 模式维持安全默认；permissive 模式可减少 ask，但仍不能绕过硬约束。
- F24: 当规则和模式都无法明确 allow/deny 时，系统必须进入人在回路确认。
- F25: 人在回路确认必须支持拒绝、本次允许、本会话允许、永久允许，以及取消。取消等价于拒绝，但原因应区分为 user_cancelled。
- F26: TUI 确认交互必须定义清晰快捷键和默认安全选项，例如拒绝/取消为默认安全路径，本次、本会话、永久允许需要用户明确选择。
- F27: 确认提示必须展示工具名、风险等级、关键参数摘要、工作目录或目标路径、触发原因、匹配规则来源或未命中说明、权限模式、允许范围影响；敏感参数必须脱敏。
- F28: 本次允许只影响当前 tool call；本会话允许生成内存规则；永久允许写入本地级权限规则文件。
- F29: 本会话允许和永久允许必须展示将生成的规则预览，并尽量生成最小规则。Bash 永久允许默认只能精确到完整命令，不得自动泛化成 `Bash(git *)` 等宽规则。
- F30: 高风险工具或高风险命令可以禁止永久允许，只允许本次或本会话。
- F31: 永久规则写入必须先 validate，写入本地级文件时应使用安全权限和原子写入；不得写入 `config.yaml`，不得记录完整敏感命令输出。
- F32: 用户拒绝、取消或权限系统拒绝时，工具不得执行，系统必须生成可恢复的 `permission_denied` tool result。
- F33: `permission_denied` tool result 必须包含结构化原因，至少区分 blacklist、sandbox、plan_mode、rule_deny、user_denied、user_cancelled、config_error。
- F34: 给模型的拒绝结果应只暴露必要原因和安全替代方向，不应暴露完整黑名单正则、权限文件路径、规则优先级细节或可用于绕过的建议。
- F35: 权限拒绝不得终止 Agent Loop；模型下一轮应能看到拒绝原因并调整策略。连续重复相同被拒绝操作时，系统应避免无限确认/拒绝循环。
- F36: Plan Mode 的只读限制必须作为硬约束生效；Plan Mode 下 Bash、Write、Edit 等非只读工具即使有 allow 规则也不得执行。
- F37: 并发工具批次中多个 ask 必须有确定策略：逐个确认、批量确认或按风险排序确认；任一拒绝都必须为对应 tool call 生成结果，并保持结果按 tool call ID 回灌。
- F38: 规则文件损坏、无法解析或权限决策异常时，危险操作必须 fail closed；TUI 应提示损坏文件、错误摘要和当前安全策略。

## 非功能需求

- N1: 黑名单、路径沙箱、Plan Mode 和权限配置保护必须 fail closed。
- N2: 权限规则加载必须确定性，优先级、同级冲突和匹配顺序可预测。
- N3: 权限拒绝结果必须结构化，便于模型理解原因和选择替代方案，但不能泄露可绕过细节。
- N4: 本章不得引入网络请求限制、资源配额或审计日志系统。
- N5: 权限系统必须兼容现有工具执行、Agent Loop、Plan Mode 和 TUI 确认流程。
- N6: 权限配置文件不得包含 API key 等秘密信息；永久允许只记录规则，不记录完整敏感命令输出。
- N7: Bash 当前只设置工作目录，不是文件系统沙箱；本章不得声称 Bash 无法访问项目外路径，必须依赖命令规则、黑名单、模式和确认控制 Bash 风险。

## 规则文件范围

- 用户级：用户配置目录下的 XAgent 权限规则文件，作为全局默认。
- 项目级：项目目录内可提交仓库的权限规则文件，覆盖用户级规则。
- 本地级：项目目录内仅本机使用的权限规则文件，覆盖项目级规则，适合保存“永久允许”，默认不应提交到 git。
- 会话级：运行期内存规则，不写入文件，不写入 conversation history，优先级最高。

具体文件名和路径在 `plan.md` 中确定。

## 规则配置格式

展示格式采用 `工具名(模式)`，用于 TUI 和摘要说明，例如：

- `Bash(git status)`
- `Bash(git *)`
- `Read(docs/**/*.md)`
- `Edit(internal/**/*.go)`

持久化 YAML 使用结构化 schema，例如：

```yaml
rules:
  - tool: Bash
    pattern: git status
    match_type: exact
    effect: allow
    description: Allow checking git status
  - tool: Edit
    pattern: internal/**/*.go
    match_type: glob
    effect: deny
```

最终字段名由 `plan.md` 固化，但必须保留可验证的结构化语义。

## 权限模式

- `strict`: 倾向最小权限。未明确 allow 的危险工具需要确认或拒绝。
- `default`: 安全默认。只读工具在路径沙箱内通常允许；危险工具需要规则或确认。
- `permissive`: 信任当前项目和用户意图。更多未命中规则的操作可默认允许，但黑名单、路径沙箱、Plan Mode 只读限制和显式 deny 仍不可绕过。

权限模式只用于未命中显式规则后的默认决策，不用于覆盖显式规则。

## 不做的事

- 不做网络请求限制。
- 不做 CPU、内存、时间、输出大小等资源配额系统。
- 不做审计日志或权限事件查询 UI。
- 不做远程策略同步。
- 不做多用户权限隔离。
- 不实现真实 OS 级 Bash 文件系统沙箱。
- 不改变现有项目路径沙箱的基本边界，只把它纳入统一权限决策流程。

## 验收标准

- AC1: 命中硬编码黑名单的 Bash 命令被拒绝，且 allow 规则、permissive 模式和用户确认都不能放行。
- AC2: 文件工具访问项目外路径或 symlink 逃逸路径时被拒绝，且不能被规则或用户确认覆盖。
- AC3: `Bash(git status)` exact allow 规则能放行精确命令，但不放行 `git status && rm -rf .`。
- AC4: `Bash(git *)` glob allow 规则只放行安全解析后的单一 git 命令族，不放行 shell 组合命令。
- AC5: `Edit(internal/**/*.go)` deny 规则能阻止匹配规范化路径的 Edit 调用。
- AC6: 本地级规则覆盖项目级，项目级覆盖用户级，会话级临时规则覆盖所有文件规则；同级冲突按确定策略处理。
- AC7: strict/default/permissive 三档模式对未命中规则的危险工具产生不同决策，但都不能绕过硬约束和显式 deny。
- AC8: 规则未明确命中时，TUI 展示确认提示，用户可以选择拒绝、本次允许、本会话允许、永久允许或取消。
- AC9: 本次允许只执行当前 tool call；本会话允许对后续匹配 tool call 生效；永久允许写入本地级规则文件。
- AC10: 永久允许写入前展示最小规则预览；Bash 永久允许默认不自动泛化成宽规则。
- AC11: 权限拒绝时工具不会执行，conversation 中保存结构化 `permission_denied` tool result，Agent Loop 继续下一轮。
- AC12: Plan Mode 下写工具或 Bash 即使有 allow 规则也不会执行。
- AC13: 规则文件损坏或无法解析时，危险操作 fail closed，TUI 显示可诊断错误。
- AC14: 给模型的拒绝结果不暴露完整黑名单正则或可绕过细节。
- AC15: 多工具批次中部分工具被拒绝时，每个 tool call 都有对应结果，Agent Loop 可继续。
- AC16: 全量测试、工具 smoke、Agent Loop smoke 通过，端到端场景能观察权限确认和拒绝后的模型调整。
