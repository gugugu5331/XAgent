# XAgent Agent Loop Spec

## 背景

XAgent 已具备 TUI、多轮对话、流式模型响应、会话持久化、OpenAI/Anthropic Provider、统一工具系统、工具执行结果回灌和基础工具行展示能力。上一阶段的工具系统让模型可以在一次回复中请求工具，并在工具结果回灌后生成最终回复。

当前限制是：模型只能“一步一停”。如果任务需要连续读取、搜索、修改、验证，用户必须反复催促模型继续。Agent Loop 章节的目标是让 XAgent 从被动应答升级为可自主推进任务的 Agent：模型可以在一次用户请求内反复观察、调用工具、读取结果、调整下一步，直到任务完成或触发安全停止条件。

本章延续现有工具系统的安全边界和 TUI 展示方式，但把“一次工具回灌后停止”升级为“多轮工具回灌直到完成”。本章不引入新的权限系统、上下文压缩或新的交互式确认机制。

## 目标

- 支持 ReAct 风格自主循环：模型回复、工具调用、工具结果回写可以连续发生多轮。
- 支持明确停止条件，避免无限循环和不可控执行。
- 提供与界面解耦的异步事件流，让 UI 只消费状态和结果，不关心循环内部实现。
- 保持流式体验：文本实时展示，同时系统保留完整响应用于判断下一步和保存会话。
- 支持一次模型响应返回多个工具调用，并按安全性和原始顺序决定并发或串行执行。
- 支持消息前缀形式的两段式 Plan Mode：`/plan` 只允许读类工具生成计划，`/do` 使用全工具执行任务。
- 保持现有普通对话和单工具场景可用。

## 功能需求

- F1: 系统在一次用户请求内可以进行多轮 ReAct 循环：请求模型、接收文本和工具调用、执行工具、回写工具结果、再次请求模型。
- F2: 当模型完成文本回复且不再请求工具时，系统结束本次 Agent Loop。
- F3: 系统必须支持最大迭代次数；默认最大迭代次数为 10，达到上限时停止循环，并向用户展示可观测的停止原因。
- F4: 用户取消或上层上下文取消时，系统必须停止当前循环，停止继续请求模型或启动新工具。
- F5: 模型连续请求未知工具达到限制时，系统必须停止循环；默认连续未知工具限制为 2 次。
- F6: 模型流式响应或 Provider 发生错误时，系统必须停止循环，向用户展示错误，并保留已产生的会话内容。
- F7: 系统需要通过异步事件流输出文本增量、思考增量、工具调用、工具运行状态、工具结果、Token 用量、循环进度、完成和错误。
- F8: 流式收集必须双路工作：文本和思考增量实时推送给界面，同时完整收集本轮响应内容用于会话保存和后续判断。
- F9: 如果一轮模型响应中先输出文本再请求工具，系统必须先保存该轮已完成的文本，再执行工具并继续下一轮。
- F10: 一次模型响应返回多个工具调用时，系统必须按模型返回的原始顺序分批处理。
- F11: 连续的安全且无副作用工具调用可以组成并发批次执行。
- F12: 有副作用或危险的工具调用必须按模型返回顺序串行执行，且不能与其他工具并发执行。
- F13: 混合工具调用必须保持原始顺序语义：后面的安全工具不能越过前面的有副作用工具提前执行。
- F14: 多个工具调用的结果都必须回写到会话历史，并能被模型在下一轮看到。
- F15: 并发工具的结果回写顺序必须与模型原始工具调用顺序一致。
- F16: 工具执行失败不能中断进程；失败结果必须作为工具结果回写，除非触发明确停止条件。
- F17: 普通没有工具调用的对话仍保持现有流式输出体验。
- F18: `/plan` 消息前缀会启动只读计划模式；该模式下模型只能使用读类工具观察项目，并最终输出计划，不允许写文件、改文件或执行命令。
- F19: `/do` 消息前缀会启动执行模式；该模式下模型可以使用全量已注册工具执行任务。
- F20: `/plan` 和 `/do` 都只影响当前用户请求的执行模式，不创建新的持久模式开关。
- F21: `/do` 可以利用当前会话历史中的上一条计划，但不要求系统额外保存独立的计划对象。
- F22: 在计划模式中，如果模型请求非只读工具，系统必须拒绝执行，把拒绝作为工具结果回写，并继续让模型生成可执行计划或停止。
- F23: `/plan` 和 `/do` 前缀不应作为普通用户内容原样发送给模型；模型看到的是去掉前缀后的任务内容和对应模式约束。
- F24: Agent Loop 的事件流必须能让 TUI 展示当前迭代进度，例如第几轮、是否达到上限、当前工具批次状态。
- F25: Agent Loop 完成或停止时必须输出明确停止原因，至少包括：正常完成、达到迭代上限、用户取消、连续未知工具、Provider 流错误。
- F26: 现有会话历史中工具调用和工具结果的顺序必须保持 Provider 可接受的协议顺序。
- F27: 如果循环中途取消、达到上限或出错，系统必须保存已经完成的用户消息、assistant 文本、工具调用和工具结果。
- F28: 如果 Provider 提供 Token 用量，系统必须通过事件流输出；如果 Provider 未提供，用量事件可以缺省，但不能影响循环完成。
- F29: Agent Loop 必须兼容现有危险工具确认行为；本章不新增权限记忆或新的确认入口。

## 非功能需求

- N1: 默认最大迭代次数必须有限，且后续可配置；默认值 10 用作本地开发任务的安全兜底。
- N2: Agent Loop 不应阻塞 TUI 主循环；模型流、工具执行和 UI 更新必须通过事件流解耦。
- N3: 并发工具执行必须保证结果回写顺序稳定，便于复现和测试。
- N4: 有副作用工具不能因为并发执行而产生不可预测的文件或命令执行顺序。
- N5: 事件命名和载荷应保持 Provider 无关，UI 不需要知道底层是 OpenAI 还是 Anthropic。
- N6: 停止条件必须可观测，用户能区分“正常完成”“达到上限”“取消”“未知工具过多”“流错误”。
- N7: 本阶段保持现有工具安全边界：文件路径仍限制在项目根目录，工具输出仍需要截断和结构化错误。
- N8: 本阶段不引入新的权限记忆或持久授权能力。
- N9: 本阶段不引入上下文压缩；如果历史变长导致 Provider 报错，按流错误停止处理。
- N10: 新增 Agent Loop 后，现有工具系统单元测试和 smoke 场景不能退化。
- N11: 并发执行只用于无副作用工具；安全性判断必须基于工具自身风险级别，而不是模型声明。
- N12: 循环进度和停止原因应以机器可读事件表示，TUI 文案只是其中一种展示方式。
- N13: Plan Mode 的只读限制必须由系统执行，不能只依赖提示词要求模型自觉遵守。

## 不做的事

- 不实现权限系统或“以后总是允许”的持久化授权。
- 不实现上下文压缩、历史摘要、长期记忆或 token 自动裁剪。
- 不实现新的用户交互式确认机制；本章只兼容已有危险工具确认行为。
- 不新增网络、浏览器、MCP、GitHub、PR、Issue 等工具。
- 不实现跨会话自动继续任务。
- 不实现后台无人值守任务队列。
- 不实现复杂沙箱、容器隔离或系统级权限隔离。
- 不改变现有 Provider 的外部配置格式。
- 不要求 Plan Mode 使用独立 UI 页面；本章只实现 `/plan` 和 `/do` 消息前缀入口。
- 不要求 `/plan` 产出的计划被结构化保存为独立实体；计划作为普通会话内容保留。
- 不要求 Token 用量在所有 Provider 上都一定存在；只在可获得时透出。

## 验收标准

- AC1: 给定需要连续读取和搜索的任务，系统能在一次用户请求内执行多轮模型请求和工具调用，直到模型输出最终文本。
- AC2: 当模型不再请求工具时，系统正常结束循环并发送完成事件，停止原因是正常完成。
- AC3: 当循环达到最大迭代次数时，系统停止继续请求模型，TUI 能看到达到上限的停止原因。
- AC4: 当上下文取消时，系统停止循环，不再启动新的模型请求或工具执行。
- AC5: 当模型连续请求未知工具达到限制时，系统停止循环并展示未知工具停止原因。
- AC6: 当 Provider 流返回错误时，系统停止循环并展示错误。
- AC7: UI 能实时收到文本增量，同时最终会话历史保存完整 assistant 文本。
- AC8: 如果一轮模型先输出文本再请求工具，该文本会出现在工具行之前，并保存进会话历史。
- AC9: 工具调用事件、工具运行事件、工具结果事件、Token 用量事件和循环进度事件都能被 TUI 消费并展示或忽略。
- AC10: 一次返回多个安全读类工具调用时，系统能执行所有工具并回写所有结果。
- AC11: 多个并发安全工具的结果在会话历史中按模型原始工具调用顺序排列。
- AC12: 一次返回多个包含副作用的工具调用时，系统按串行顺序执行并回写所有结果。
- AC13: 混合工具调用不会让后面的安全工具越过前面的副作用工具提前执行。
- AC14: 工具失败结果会回写给模型，模型可以在下一轮基于失败结果调整。
- AC15: 普通无工具对话仍能流式输出并正常保存。
- AC16: 输入 `/plan <任务>` 时，系统只允许读类工具；模型请求写、改或命令工具时不会执行。
- AC17: `/plan` 最终输出计划文本，不对项目产生写入或命令副作用。
- AC18: 输入 `/do <任务>` 时，系统使用全量工具执行任务。
- AC19: `/plan` 和 `/do` 前缀不会原样出现在发送给模型的用户任务内容中。
- AC20: `/plan` 和 `/do` 只影响当前请求；后续普通消息不会自动继承计划模式或执行模式。
- AC21: 工具调用和结果在会话历史中的顺序满足 OpenAI 和 Anthropic 的工具协议要求。
- AC22: 循环中途取消、达到上限或出错后，已经完成的消息和工具结果会被保存。
- AC23: 现有 `go test ./...` 通过。
- AC24: 现有工具 smoke 场景通过，并新增 Agent Loop smoke 或端到端场景通过。
